# Runbook: backup/restore/перенос (T14)

## Решения (записаны, не переспрашивать)

**D06 (2026-09-25, владелец):** хранилище — каталог на текущей машине
(`BACKUP_DIR` в env профиля); RPO 24ч / RTO ≤2ч; retention GFS 7 дневных + 4
недельных; шифрование — age (симметричный ключ-файл `age-keygen`, права 600, вне git;
интерактивный `age -p` для автоматики непригоден — читает пароль только с TTY).
**Принятый зазор (п.7 плана):** копия на том же диске не защищает от потери
диска (B05). Это осознанная временная мера до Linux-переезда (T18), где тот же
набор скриптов пишет в независимое хранилище — тогда B05 проверяется по-настоящему.

**D09 (политика остановки записи, принята ранее):** согласованность снимка
достигается полной остановкой app-сервисов (`compose stop` без mongo/nats).
Сервисы с T12 корректно дренируют задачи по SIGTERM, поэтому окно заморозки =
« writers гарантированно не пишут», и `consistentSnapshot: true` в манифесте —
доказуемое утверждение, а не надежда на `mongodump` в живой БД.

## Инвентарь источников (п.1)

| Источник | Где | Как попадает в снимок |
|---|---|---|
| БД `voice_tracker` (Windows mongod до T18; контейнер mongo после) | порт 27017 / compose | `mongodump --archive` внутри mongo-контейнера |
| Media | docker volume `MEDIA_VOLUME` (name из env) | одноразовый контейнер `tar` с примонтированным volume (RW-писатель заморожен) |
| Конфигурация вне git | env-файлы профиля + age-ключ | НЕ включаются в архив приватных данных; секретные значения не печатаются и в манифест не попадают (валидируется `backup_manifest.py build`) |
| Шемы | `schema_versions` в БД + манифест T10 | `schemaVersion` фиксируется в manifest.json |

Старые `cleanup_*.js`/`run_backup.cmd` — не исполнять (п.1 плана); этот runbook
их заменяет.

## Ежедневный запуск (п.8)

Linux (целевой хост, systemd-таймеры из `deploy/backup/systemd/`):

```bash
sudo systemctl enable --now dsbot-backup.timer dsbot-backup-status.timer
systemctl list-timers 'dsbot-backup*'   # последний/следующий запуск (B06)
journalctl -u dsbot-backup.service -n 50
```

Windows (до T18, через WSL; планировщик ОС):

```
schtasks /Create /TN dsbot-backup /SC DAILY /ST 04:30 ^
  /TR "wsl.exe -d Ubuntu-22.04 bash -lc \"/opt/dsbot/deploy/backup/backup.sh production >> /var/log/dsbot-backup.log 2>&1\""
```

Ротация (`backup_retention.py`, GFS): удаляются только проверенные точки вне
7 дневных/4 недельных; **последняя проверенная защищена всегда**; каталоги без
`.verified_ok` (упавший запуск) автоматически не удаляются и в ротации не
участвуют — B02: предыдущая копия неуспешным запуском не затирается.

Свежесть (B06): `deploy/backup/backup_status.sh <profile>` — exit 1, если
возраст последней проверенной точки > `BACKUP_MAX_AGE_HOURS` (default 26h),
либо проверенных точек нет вовсе.

## Репетиция восстановления (п.5/п.6, обязательна перед T18; R26-08)

```bash
deploy/backup/restore.sh staging --state /var/tmp/dsbot-restore-staging.json
# → цель БД: voice_tracker_<profile>_rehearsal_<YYYYMMDDTHHMMSSZ>_<hex6> — генерируется
#   прогоном и проверяется строгим allowlist (restore_targets.py validate-db); совпадение
#   с source или настроенной БД (MONGO_DB) — отказ;
# → media-volume ВСЕГДА новый dsbot-<profile>-restore-media-<runid>; имя извне не
#   принимается (--media-volume удалён); перед create выполняется inspect: существующий
#   volume = отказ до любой записи; после create сверяется метка
#   com.dsbot.restore.run=<runid> — «docker volume create» молча возвращает существующий
#   ресурс, поэтому без перечитки метки новизна цели недоказуема;
# → перед mongorestore список БД (listDatabases, имя цели НЕ интерполируется в JS)
#   проверяется повторно — цель обязана отсутствовать (гейт гонки); записи без --drop,
#   распакованный media-tar проходит check-tar (без traversal/ссылок/спец-файлов,
#   потолок размера = media.bytes из манифеста × 2) до первой записи в volume; после
#   распаковки владелец ставится DSBOT_UID:DSBOT_GID из env профиля;
# → checksums и манифест проверяются ДО любой записи (B04);
# → verify ОБЯЗАТЕЛЕН всегда: counts против манифеста, индексы через каноническую
#   сверку схемы (T10), revision в guild_settings, наличие каждого media-файла по
#   attachments.path, schemaVersion. Флага обхода нет: --no-verify УДАЛЁН, «зелёный»
#   выход без проверок структурно невозможен;
# → после успеха цели удаляются, но cleanup трогает ТОЛЬКО свои цели: БД — если имя
#   проходит allowlist-regex и state-файл подтверждает фазу db-restored этого же run id;
#   volume — только с совпавшей ownership-меткой (чужой ресурс не удаляется никогда,
#   даже если его имя когда-либо было передано аргументом). --keep оставляет цели.
```

Никогда не указывать живой destination для репетиции — скрипт делает это структурно:
media-имя извне не принимается, целевое имя БД ограничено rehearsal-allowlist, а
существующая цель (БД или volume) = отказ до первых записей.

### State-файл прогона, повторный запуск и resume

Прогон ведёт JSON state-файл (по умолчанию `<BACKUP_DIR>/.restore-<profile>-state.json`,
лучше задавать явно через `--state`): run id, режим, обе цели, точка-источник и фазы
`prepared → media-extracted → db-restored → verified → cleaned`, при отказе —
`failed:<этап>` (диагностика не затирается, plaintext-media с диска убирается всегда).

* Повторный запуск с тем же `--state` без `--resume` = отказ: «повтор в один час»
  больше не коллидирует с незавершённым прогоном (run id теперь полной точности
  с энтропией, но state-файл — это ещё и резервация целей).
* `--resume` сверяет run id / цели / режим / точку из state с текущими; при
  несовпадении — отказ. Совпало — прогон продолжает с недойденной фазы
  (завершённые шаги пропускаются). Resume завершённого (cleaned) прогона запрещён —
  делайте новый запуск (удалив/сменив state-файл).
* Отказ на любом шаге оставляет `failed:*` в state; свои цели (подтверждённые state)
  убираются cleanup'ом rehearsal-режима, чужие не удаляются никогда.

### Режимы rehearsal и cutover

`--mode rehearsal` (по умолчанию) — изолированная репетиция: только allowlist-цели,
cleanup своих целей разрешён.

`--mode cutover` — перенос на чистый хост (T18). Целевое боевое имя принимается
ТОЛЬКО с явным `--confirm-dest <точное имя>`, совпадающим с `--into-db`; state-файл
фиксирует `mode=cutover`. Цель обязана отсутствовать на сервере (listDatabases/volume
inspect = отказ при существовании). `--keep` форсируется: cleanup и какие-либо
удаления существующих ресурсов в cutover запрещены; в отчёт пишутся mode/keep.
Активация (перевод MONGO_DB/MEDIA_VOLUME env профиля на восстановленные цели) —
отдельный осознанный шаг оператора.

## Перенос Windows → Linux (п.9–11; исполняется на T18, не раньше)

1. На Linux развёрнут каркас T13 (образы по digest'ам, тома созданы
   `linux_init.sh`, приложение НЕ запускается).
2. Предварительная репетиция: обычный `backup.sh` (Windows) → перенос точек на
   Linux с checksum → `restore.sh <profile> --state FILE` (режим `rehearsal` по
   умолчанию: цели генерируются прогоном, ownership-метки, обязательный verify) →
   `migrate.py check` (T10) → замеры (B07). Репетиция ничего не меняет в проде;
   повтор после отказа — тем же `--state --resume`, новый прогон — с новым
   `--state` (занятый state-файл блокирует повтор как резервацию чужого прогона).
3. Окно переноса: `backup.sh production` (заморозка writers входит в снятие);
   с этого момента Windows-writers не поднимаются (п.10: два активных
   писателя к расходящимся БД недопустимы — старый набор остаётся остановленным).
4. Перенос последних точек + `restore.sh production --mode cutover --into-db
   voice_tracker_production --confirm-dest voice_tracker_production --state FILE`
   в боевые имена на Linux: цель обязана отсутствовать на сервере (на чистой
   машине — отсутствует), `--keep` форсится, удаления существующих ресурсов
   скриптом запрещены. Затем активация env профиля на восстановленные цели,
   consumers → gateway → entrypoints (порядок T13 `deploy.sh`), read-only smoke
   (web `/api/readyz`, heartbeat CLI), затем снятие ограничений и первая запись
   на Linux.
5. Голосовая сессия на границе (п.11): если в момент заморозки была активна
   voice-сессия, интервал между freeze и resume на Linux НЕ является точно
   восстановленной историей — reconciliation на Linux догонит по Discord-аудиту
   (H-механика T11) и закроет интервал с явной границей; лишний session.close
   запрещён контракт event_id (T09). Пауза не «дорисовывается» задним числом.
6. Возврат после первой записи на Linux — это не «restart старого контейнера»,
   а обратная миграция данных (restore Windows ← Linux-снимок). Учитывать при
   любом плане «отката» после cutover.

## Границы честности

- Монотонность B07: замеры на репетиции — по фактическому объёму на дату
  репетиции; расхождение с целями D06 пишется в PROGRESS как есть.
- `mongodump` на standalone без заморозки writers не обещает межколлекционной
  консистентности — поэтому `consistentSnapshot` ставится только внутри окна
  заморозки, и ни при каких обходных запусках (флаг в скрипте отсутствует).
