# Runbook: квота диска и сохранение архива (T16)

## Что решено владельцем (D04/D07)

- Удалённые в Discord сообщения и вложения **сохраняются** в нашем архиве:
  контент остаётся, ставится только tombstone `deletedAt`.
- **Срок хранения пользовательского контента не утверждён.** Пока он не
  назначен, никакой автоматический «janitor» старые данные не удаляет —
  ни по TTL, ни по размеру диска, ни «чтобы освободить место».
- Резервные копии (`BACKUP_*`, [runbook-backup.md](runbook-backup.md)) и
  пользовательский контент (`RETENTION_*`) — разные параметры и разные решения.

## Квота свободного места (L05)

Бот перед скачиванием вложения проверяет свободное место на томе `MEDIA_DIR`
(`voice_tracker/media.py`). Порог задаётся переменной окружения:

- `MEDIA_MIN_FREE_BYTES` — сколько байт должно оставаться (по умолчанию
  2 GiB). `0` отключает проверку.

При нехватке места поведение **безопасное и честное**:

1. Новые вложения не скачиваются; в метаданных сообщения остаётся
   `stored=false`, `url` (ссылка Discord) и `storeSkipReason="disk-quota-low"`.
2. Веб-интерфейс показывает причину вместо «загрузка навсегда».
3. Существующий архив не трогается никогда. Освобождение места — только
   ручное решение оператора после назначения срока (см. ниже).

Веб (`sklep-ds-bot-web`) при низком остатке добавляет предупреждение в
`/api/readyz` (`warnings: ["media disk quota low"]`), но остаётся `ready`:
чтение уже сохранённого архива от нехватки места не страдает, а снимать
готовность сервиса из-за предупреждения о диске значило бы уронить UI
задолго до реальной проблемы.

## Как обнаружить проблему заранее

- Бот пишет в лог `media disk quota low: ...` (не чаще раза в 5 минут).
- `/api/readyz` на вебе показывает `media.quotaLow=true` и `media.freeMB`.
- Плановый отчёт: `python -m voice_tracker.retention report ...` (см. ниже).

## Dry-run отчёт о retention (удалений НЕ делает)

```bash
python -m voice_tracker.retention report \
  --uri "$MONGO_URI" --db "$MONGO_DB" \
  --media-dir "$MEDIA_DIR" \
  --deleted-days 365   # переопределить RETENTION_DELETED_DAYS для пробы
```

Возвращает JSON: сколько tombstone-записей попали бы в выборку при таком
сроке (`deletedMessages`) и сколько файлов на диске не имеют ссылок из
архива (`orphanMedia`). Это только план.

## Если диск всё-таки заполнился

1. Убедиться, что новые загрузки остановились (в логе есть `quota low`, в
   свежих сообщениях `storeSkipReason="disk-quota-low"`).
2. Освободить место вне архива (временные файлы, старые **резервные копии**
   по runbook-backup.md). Архив сообщений/вложений — не место для расчистки.
3. **Не удалять** сохранённые вложения ради места. Удаление пользовательского
   контента возможно только после отдельного решения владельца о сроке
   хранения; до него механизма удаления в коде нет намеренно.
4. Когда срок будет назначен, удаление станет отдельной задачей с
   собственным решением и ревью, а не флагом в этом отчёте.
